# GlobalShop 全服商店

> [English](README.md) | **简体中文**

一个 **服务端权威的全服共享商店**，适用于 Minecraft Java 版 1.20.1（Forge）。内置经济系统，
**不依赖 Vault，也不依赖任何第三方经济模组**。

服务器上所有玩家在 **同一个** 市场里交易。余额、商品、托管库存和商品所有权全部存放在
**服务端的世界存档** 里。客户端只负责绘制服务端发给它的内容。

## 2. 构建

```bash
# Linux / macOS
./gradlew build

# Windows
gradlew.bat build
```

产物位于 `build/libs/globalshop-1.0.0.jar`。

> **如果 `gradlew` 下载不了 Gradle**：wrapper 默认指向镜像源，因为
> `services.gradle.org` 会跳转到 GitHub，而部分网络环境访问不到。
> 请编辑 `gradle/wrapper/gradle-wrapper.properties`，把 `distributionUrl` 改成你能访问的那个：
> * `https://services.gradle.org/distributions/gradle-8.1.1-bin.zip`（官方）
> * `https://mirrors.cloud.tencent.com/gradle/gradle-8.1.1-bin.zip`（本工程的默认值）
>
> 如果你本机已经装了 Gradle 8.1.1，也可以直接 `gradle build`，完全不用 wrapper。

## 3. 安装

把 `globalshop-1.0.0.jar` 放进 `mods/` 文件夹。

### 客户端与服务端 —— 这一点很重要

GlobalShop 是 **服务端权威** 的。数据由服务端存储，所有决定（价格、库存、余额、所有权）
都由服务端做出。

* **多人服务器：模组必须装在服务端。** 客户端装了模组但连到一个没装的服务端时，无法打开
  市场、无法使用指令、也无法改动余额——因为服务端根本不认识这些指令和这个网络通道。
* **客户端：** 安装相同版本的 jar。Forge 会校验网络协议版本，且 GUI 与物品需要在两端都存在
  才能正常显示。没装模组的客户端会看到一个未知物品和一个打不开的方块，无法使用市场。
* **单人 / 局域网：** 内置服务端就是权威，所以数据依然写进该世界自己的 `data` 目录，
  **绝不会**写到某个全局的客户端位置。

## 4. 数据存放在哪里

这是硬性设计约束，不是实现细节。

| 内容 | 位置 | 说明 |
|---|---|---|
| 余额 | `<世界存档>/data/globalshop_economy.dat` | 服务端 `SavedData`。按 **玩家 UUID** 存储，因此改名不会丢钱，离线玩家也保留余额。 |
| 商品、托管库存、所有权、信箱 | `<世界存档>/data/globalshop_shop.dat` | 同一机制。整个服务器共享，随世界存档一起备份。 |
| 交易日志 | 存在 `globalshop_shop.dat` 内部 | 上限为 `tradeLogRetention` 条，超出时优先丢弃最旧的。 |
| 策略配置（初始余额、价格上限等） | `config/globalshop-common.toml` | **只放策略。** 余额、库存、所有权绝不会写进配置文件，所以改配置文件无法凭空造钱或造物品。 |

在专用服务器上路径是 `<服务器根目录>/world/data/globalshop_*.dat`；
在单人 / 局域网世界上是 `<saves>/<世界名>/data/globalshop_*.dat`。

**任何权威数据都不会写到客户端。** 客户端只持有一份显示用缓存，每次请求页面都会被整体替换，
断线时会被丢弃，因此重新连接永远从服务端的状态开始。

### 所有权与身份

账户按 UUID 存储。名字只是为了指令输出和日志能显示出可读内容才记录的，
**从不** 用作身份标识。

## 5. 指令

| 指令 | 权限 | 作用 |
|---|---|---|
| `/money` | 所有人 | 查看自己的余额。 |
| `/pay <玩家> <金额>` | 所有人 | 向其他玩家支付。会拒绝 0、负数、支付给自己、以及超过自己余额的金额。 |
| `/money <玩家>` | OP（等级 2） | 查看指定玩家的余额。离线玩家同样可用。 |
| `/money give <玩家> <金额>` | OP（等级 2） | 加钱。 |
| `/money take <玩家> <金额>` | OP（等级 2） | 扣钱。拒绝扣成负数。 |
| `/money set <玩家> <金额>` | OP（等级 2） | 直接设置余额。 |
| `/shop` | 所有人 | 打开市场。 |
| `/globalshop` | 所有人 | 打开市场。 |
| `/globalshop open` | 所有人 | 打开市场。 |
| `/globalshop claim` | 所有人 | 领取属于你的物品（离线期间产生的返还）。 |
| `/globalshop money …` | 同 `/money` | 备用入口，防止别的模组占用了 `/money`。 |
| `/globalshop pay …` | 同 `/pay` | 备用入口，防止别的模组占用了 `/pay`。 |
| `/globalshop reload` | OP（等级 2） | 重新应用配置并持久化市场数据。 |
| `/globalshop logs [条数]` | OP（等级 2） | 查看最近的交易日志。 |
| `/globalshop ids [条数]` | OP（等级 2） | 列出商品 ID，让 `/globalshop remove` 可用。 |
| `/globalshop remove <ID>` | OP（等级 2） | 强制下架指定商品。未售出物品返还给卖家（卖家可能离线）。 |
| `/globalshop selftest` | 等级 4 | 运行内置自测（见第 8 节）。 |
| `/globalshop market` | 所有人 | 打开玩家市场。 |
| `/globalshop server` | 所有人 | 打开服务器官方商店。 |
| `/globalshop server add <物品> <出售价> <回收价> <一次购买数量> [限购上限] [是否回收]` | OP（等级 2） | 上架一件服务器商品。 |
| `/globalshop server remove <物品>` | OP（等级 2） | 下架一件服务器商品。 |
| `/globalshop server list [条数]` | OP（等级 2） | 列出服务器商店目录。 |
| `/globalshop server reload` | OP（等级 2） | 重新应用时间设置并持久化。 |
| `/globalshop server resetDaily <玩家>` | OP（等级 2） | 重置指定玩家今日回收计数（调试用）。 |
| `/globalshop server logs [条数]` | OP（等级 2） | 最近的服务器商店交易记录。 |

**谁能造钱。** 只有管理员：`/money give`、`/money take`、`/money set`、`/money <玩家>`
全都是**等级 2**，而且在**两条路径**上都是（`/money …` 与 `/globalshop money …`）。
这不是读源码得出的结论——自测会**遍历服务端真正构建出来的命令树**，用权限等级 0、2、4 的
真实 source 去求值每个节点的 `requires`，再检查"玩家能够到达的命令里没有任何一个叫
`give`、`take` 或 `set`"（见第 8 节）。经济命令是通过**共享的构建器注册了两遍**的，
权限检查只要漏掉其中一条路径就是**提权漏洞**；正是这个测试排除了这种可能。

普通玩家在本模组里能够到达的命令，完整清单就是：

```
/money          /pay <玩家> <金额>      /shop        /globalshop
/globalshop open   /globalshop claim   /globalshop money   /globalshop pay <玩家> <金额>
```

`/pay` 对所有人开放是**刻意设计**：它是从**付款人自己的余额**里转账、拒绝自我支付、
且是一次原子的"扣+加"，所以玩家无法用它造钱。（不带参数的 `/pay` 和 `/globalshop pay`
虽然可以被遍历到，但没有执行器，Brigadier 会报"命令不完整"而不会执行任何东西。）

**金额** 同时支持整数与小数写法：`10`、`12.34`、`.5`、`1,234.50`。
它们会用精确十进制运算解析成最小货币单位，因此指令**不可能**引入浮点舍入误差。

## 6. 市场用法

**获取终端。** *全服商店终端* 在 GlobalShop 创造模式标签页里。右键地面即可放置，
然后右键那个方块就能打开市场。**不需要空手、也不需要特定工具**——拿着任何东西右键都有效，
这是商店类方块的常规便利做法。按住潜行键则会穿透过去，
所以你仍然可以对着终端放置方块。

**上架。** 把要卖的物品堆放进 **上架槽** —— 它位于背包右侧、有自己独立的凹槽括位，而且在**每个标签页都会显示**，所以位置永远不会变成猜测。然后打开 *上架* 标签页，设置：

* 单价
* 库存（总共上架多少个）
* 最少一次购买几个
* 最多一次购买几个

库存随后会被 **托管**：物品立刻从上架槽和你的背包中扣除，由商店持有。
因此一个商品**绝不可能**发出卖家当初没有真正交出来的东西。**上架超过一组也没问题**——
先扣上架槽，不足的部分从背包补扣；而且「库存」输入框会**自动填成你身上该物品的总数**，
所以"全部卖掉"不需要自己算数。

**购买。** 点击网格里的商品。右侧面板会显示卖家、单价、剩余库存、起购量、限购量、
上架时间，以及一行实时更新的 **`单价 × 数量 = 总价`**。用 `-` / `+` 或直接输入来调整数量，
然后按 *购 买*。

对于**工具类物品**，面板不只显示名称，还会告诉你这件东西本身怎么样：
**剩余耐久**以 `312/1561` 的数值显示并按剩余比例变色；**附魔**列在一行，放不下时会显示
`(+n)` 表示还有几项——如果只写一个 `...`，你无法分辨一把剑有 1 个附魔还是 5 个。

把鼠标停在**网格里任意商品上，或详情面板的物品图标上**，会弹出**完整的原版提示框**：
与背包里看到的是同一个框，由 `ItemStack.getTooltipLines` 构建——带稀有度与附魔配色的名称、
全部附魔、耐久、属性修饰符，以及模组物品自己附加的任何说明。
所以第三方模组的物品会"自我介绍"，本模组不需要为它们做任何适配。

**把商品取回来（包括误操作上架的）。** 选中**任何一件你自己的商品**，面板下方那个大按钮就会
从 *购 买* 变成 ***下 架*** —— 无论是在「市场」页还是「我的商品」页。
**不存在"你能看见自己的商品却无法下架"的状态**：购买自己的商品毫无意义，
所以那个按钮位置永远提供当下唯一有意义的操作。未售出的托管物品会直接回到你的背包；
如果你离线，则进入信箱，用 `/globalshop claim` 领取。

*我的商品* 页还可以修改单价、库存、起购、限购。提高库存会先从你的背包里扣除多出来的物品，
所以你无法把商品虚增到超过你实际拥有的数量；降低库存则会把差额退还给你。
已售罄的商品会从公开市场消失，但仍留在你自己的标签页里，方便你补货或删除。

**翻页、排序、搜索。** 网格是 6×6 = 每页 36 件，用 `<` / `>` 按钮翻页
（在网格上滚轮也可以）。可以按价格（升序或降序）、上架时间（最新或最早）或卖家排序。
在搜索框输入可按物品名称、注册名或卖家名过滤——输入做了防抖处理，
不会每敲一个字符就发一个网络包。

### 服务器官方商店

这是**第二个商店**，用途也完全不同。玩家市场让物品**在玩家之间**流动；服务器商店则对着
管理员写下的价目表，凭空向玩家收购、也凭空卖给玩家。它们是不同的方块、不同的物品、
不同的菜单、不同的界面——但**共用同一套经济**。服务器商店标题栏里的余额，就是 `/money`
打印的、玩家市场花掉的那个余额，因为三者都走同一个 `EconomyService`。
**没有第二种货币，也没有第二套账户。**

**两个方块，不是一个。** `globalshop:shop_terminal` 打开玩家市场；
`globalshop:server_shop_terminal` 打开服务器商店。两者都会出现在本模组的创造模式标签页里，
而且**都没有合成配方**——从服务器商店购买是获得它们的唯一途径。

默认情况下服务器商店**只上架一条商品**：

| 商品 | 默认价格 | 限购 |
|---|---|---|
| `globalshop:shop_terminal` —— 玩家市场终端 | 1000.00 | **每人 10 个** |

**被限购的是玩家市场终端**：它才是让玩家能把东西卖给所有人的那个方块，值得限量。
本商店自己的终端**默认完全不上架**——它只是个入口，管理员可以自己放一个，
或者用 `/globalshop server` 直接打开。两者都可配置
（`sellMarketTerminal` / `stockOwnTerminal` 及其价格与限购）。

内置商品**是否存在，是每次启动都按配置收敛的**，而不是记一个一次性的"已播种"标志。
我先试过一次性的版本迁移，那个做法不够好：在配置仍然要求上架某商品的某一次运行里，
它就把存档标记成"已是最新"，于是这次修正被消耗掉了却没生效，而且再也不会重来。
价格只在**首次创建**时写入，所以管理员的改价永远不会被覆盖；代价是手动删掉的内置商品
会在下次启动时回来，要真正去掉它请关闭对应的配置开关。
`ServerShopSavedData.DEFAULTS_VERSION` 保留下来作为"这个存档见过哪一版默认值"的记录。

### 三个页面，因为是三件不同的事

售卖与回收是**两个独立页面**，它们是方向相反、规则也相反的两件事——购买没有上限而且要花钱；
回收受每日额度限制而且会赚钱：

* **出售** —— 售价、一次购买数量、限购、以及实时更新的 `单价 × 数量 = 总价`。
* **回收** —— 回收价、背包中持有数量、已用与剩余的每日额度、以及把身上全部卖掉实际能拿到多少。
* **管理**（仅管理员）—— 写商品目录的地方。

每个交易页**只列出它真能做的商品**：没有回收价的商品不会出现在回收页，
没有售价的商品不会出现在出售页。

### 只出售、只回收、或两者都有

一条商品可以是这三种中的任意一种。**把售价设为 0 就是"只回收"**——服务器只收不进，
比如管理员想大量回收的圆石。

这里我犯过**同一个错误两次**，都值得记下来。第一次：我要求售价必须大于 0，
于是"只回收"的商品**根本无法上架**。第二次：等它能上架了，"回收价必须低于出售价"
这条规则**仍然被套用在它身上**——拿 20 去和售价 0 比较，判定 20 不低于 0，
于是每一次回收都被拒绝。商品存在，却永远用不了——这正是你反馈到的现象。

现在这条规则**只有一个实现**，上架处与交易处调用同一个方法，
并且在没有售价时**刻意不比较**。只回收的商品本身也无法被购买，所以不存在可被利用的地方。

### 在界面里写商品目录

管理页从**商品槽位**取物品——从下方快捷栏行**拖进去**，那一行就是为此而显示的。
把物品拿在手上的管理员也能用，两条路都不是死路。上架**不会消耗**物品，
关掉窗口时槽位里剩下的东西会原样还给你。

空间上只放得下**一行**快捷栏，放不下四行：9 格宽 162 像素，而 320 像素的窗口宽度受制于
854×480 屏幕所能容纳的 240 像素高度；四行需要 72 像素，而面板与按钮之间只有 26 像素。
一行能覆盖快捷栏，而要上架的物品通常就在那里；不在的话，用手持也可以。

两张贴图互为**反色**，所以在快捷栏里不可能认错。以下颜色是从实际发布的文件里**测出来的**，
不是凭印象写的：玩家市场终端是冷灰主体（`#181A20`）、配上平涂的浅蓝边框（`#4FC3F7`）
包裹暖金色的核心；服务器商店终端则反过来——暖灰主体（`#231D1C`）、平涂的金色边框（`#FFE05E`）
包裹冷蓝色的核心。

**购买不限量。** 服务器商店的库存是无限的，所以没有任何东西会减少。唯一的上限是某一行
可选的限购上限，按玩家 UUID 统计并持久化。

**回收则限量。** 这是玩家**无需他人同意**就能把物品变成钱的方向，所以有两道防线：

* 回收价必须**严格低于**出售价——上架时校验一次，**每次回收再校验一次**，因为这是防刷钱的那条规则；
* 每位玩家有**每日额度**，默认 128 个，按**物品个数**计算，**所有商品共用**这一个总额度。
  购买没有这个限制。

**每日额度跟随真实日历。** 不是世界天数、不是 tick 数、不是开服时长——那些在服务器关闭期间
都会停止推进，而这恰恰是要处理的情况。每位玩家在自己的计数旁边存一个 `lastRecycleDate`
（`yyyy-MM-dd` 字符串），**每一次读写都会先拿它和今天的日期比较**再决定行为。因此重置
**不需要定时器、也不需要补算**：跨越午夜后的第一次接触就会重置，无论服务器是通宵运行、
第二天早上才重启，还是停机了整整一周。时区可配置（`serverShop.timezone`），
配置了无法识别的时区会回退到服务器本地时区并记一条警告，而不是让回收功能崩掉。

可选地，日期也可以改从 NTP 服务器获取（`serverShop.useOnlineTime`）。该查询**在后台执行并缓存
结果**——**绝不在交易路径上联网**，否则一个缓慢或不可达的授时服务器就会卡住服务端线程。
查询失败时使用系统时钟并记录警告；无论哪种情况，回收功能都照常工作。

界面会显示管理员设定的三个购买数字（已购买 / 限购上限 / 还可购买）和三个额度数字
（今日已回收 / 每日上限 / 今日剩余可回收），以及物品自身的耐久与附魔，
鼠标悬停时还会显示完整的原版提示框。

### 与第三方模组物品的兼容性

**兼容。** 一个商品是以「注册名 + 物品的完整 NBT」形式存储的，所以任何已注册物品都可以上架。
代码里没有任何针对特定原版物品的判断，而且搜索框也会匹配注册名——
输入 `create` 就能列出那个模组的物品。

有五点需要注意：

* **同一个商品必须由逐字节相同的副本组成。** 托管匹配用的是
  `ItemStack.isSameItemSameTags`，因此任何 tag 有差异的两个物品都会被当作不同物品。
  一把 50% 耐久的镐子和一把满耐久的镐子**无法**合并成一个"库存 2"的商品，
  内容物不同的两个背包同样不行。这是**刻意设计**：正是它阻止了用便宜物品替换贵重物品。
* **商品存的是"模板 + 数量"。** 买家收到的每一个副本都是模板的**完全相同克隆**。
  对普通的可堆叠物品这完全正确；但对"每个副本本应各不相同"的物品（例如随机词缀），
  所有副本都会带上模板的数值，而不是各自的。
* **只存在于 capability 而不在 NBT 里的状态不会被保留。** 这是 `ItemStack.save` 的性质，
  不是本模组造成的，但它影响的正是同一类物品。
* **移除提供某物品的模组后，相关商品会失效。** 加载时已不存在的物品 ID 会解析成空气，
  于是该商品（以及信箱里的对应条目）会被丢弃，托管的物品也随之消失。
  卸载内容模组之前请先备份世界。
* **目前没有物品黑名单。** `ShopResult.FORBIDDEN_ITEM` 已声明但从未被返回，
  所以玩家能拿在手里的任何东西都能上架。如果需要限制，加一个由配置或物品标签驱动的
  黑名单是最自然的做法。

## 8. 测试

### 自动测试：内置自测

模组可以对着 **真实运行中的服务端** 验证自己。它使用 Forge 的 `FakePlayerFactory` 取得
真正的 `ServerPlayer` 实例，因此跑的就是处理真实购买的那条代码路径。

**游戏内**（等级 4 的 OP）：

```
/globalshop selftest
```

**无头运行**（适合放进 CI）：以系统属性启动专用服务器，它会在启动时跑完检查然后自动停止服务器。

该属性必须传到 **服务端** 的 JVM，而不是 Gradle 守护进程。两种做法：

```groovy
// build.gradle 的 "server" run 块里
server {
    jvmArgs '-Dglobalshop.selftest=true'   // 该行已存在，只是被注释掉了
}
```

然后

```bash
./gradlew runServer
```

或者不改构建脚本，直接给被启动的 JVM 设置环境变量：

```bash
# Linux / macOS
JAVA_TOOL_OPTIONS=-Dglobalshop.selftest=true ./gradlew runServer

# Windows PowerShell
$env:JAVA_TOOL_OPTIONS = "-Dglobalshop.selftest=true"; ./gradlew.bat runServer
```

结果会以一系列 `[selftest] PASS/FAIL` 行的形式出现在服务端日志里，最后一行是
`RESULT n passed, m failed, k skipped`。一次干净运行的结果是
`RESULT 492 passed, 0 failed, 0 skipped`。该测试是**可重复**的：它会删除自己创建的商品、
清空它用过的信箱、并恢复它动过的余额，所以对同一个世界连着跑两次结果一致。
它确实会留下两个保留账户（`GS_Alice`、`GS_Bob`），余额为 0。

> 要运行 `runServer`，你必须自行接受 Minecraft EULA：创建 `run/eula.txt`，
> 内容为 `eula=true`。

#### 自测覆盖了哪些内容

**金额算术**：余额能正确读回；`hasEnough` 在等于余额时为真、超过时为假；0 与负数被拒绝；
透支被拒绝**且余额保持不变**；转账同时扣款与入账；禁止支付给自己；余额不足的转账被拒绝
**且双方余额都不变**；双方余额之和守恒；会导致溢出的入账被拒绝，而不是回绕成负数。

**市场**：上架会精确托管所申报的数量；商品对其他玩家可见且能按名称搜到；数量低于起购、
高于限购、超过库存、购买自己的商品、以及不存在的商品，都会各自以**具体原因**被拒绝；
一次购买移动的金额与物品数量都**精确正确**；余额不足的购买不会改变金钱、库存或物品；
改价生效；互相矛盾的数量限制被拒绝；非所有者无法修改；下架会返还剩余托管物品。

**持久化**：余额、账户列表、商品数量、交易日志、商品的物品、库存、价格和所有权，
全都能通过一次"序列化 → 重新读取"的往返，而这正是服务器重启所做的一切。

**携带 NBT 的物品**：一把带自定义名称、两个附魔和耐久损耗的剑，会被上架、存储、往返读写并被购买，
且买家收到的那一份 tag **逐字节相同**。这正是第三方模组物品所依赖的机制——
普通的圆石不含 NBT，所以即使所有 tag 都被丢弃它也照样能通过。同一条商品还会被推过**真实的网络包编解码器**，
这是全项目唯一测试网络序列化的检查，它证明了详情面板确实能收到用来显示附魔与耐久的数据。

**节流**：同一玩家紧接着的第二次购买会以 `COOLDOWN` 被拒绝。

**命令树序列化**：命令树里每一个参数类型都已在客户端同步注册表中登记，并且整棵树会**真的**通过服务端玩家登录时所调用的那个方法序列化一遍。这一组检查的存在是因为曾经出过一次
线上 bug——一个未注册的自定义参数类型让 `Commands.sendCommands` 抛异常，于是**每次登录都被
拒绝**并提示"无效的玩家数据"，而当时其余的测试完全没发现，因为假玩家从不走登录流程。
**不要在未替换为仍能覆盖该路径的检查前删掉它们。**

**界面数据**：界面据以绘制的那份页面数据，会把查看者自己的商品标记为"他的"（下架按钮正是
依据这个标记出现）、不会把别人的商品标成自己的、会把已售罄的商品保留在其卖家自己的页面里
（便于补货或删除）、并在公开市场中隐藏它们。

**命令权限**：会用权限等级 0、2、4 的真实 source 遍历服务端构建出的命令树，断言每一条
"能移动金钱"的命令在**它的两条注册路径上**都对玩家不可达，并额外做一次全局扫描，
断言玩家可达的命令里没有任何一个名为 `give`、`take` 或 `set`。只读 `.requires(...)`
是无法发现"权限检查只落在两条路径之一"的。遍历只对本模组自己的子树做全量，其余命令只扫一层：
Brigadier 的命令树是**带共享节点的 DAG**，按路径全量枚举会组合爆炸——早先的版本就是这样
把整次服务端运行挂死，直到给遍历加上边界才结束。

**跨来源托管**：当上架槽里只有 64 个、背包里还有 64 个时，上架 128 个会成功，并从两处一起扣除、
不留残余；而多要 1 个（超出实际持有量）依然会被拒绝且不产生任何改动。这一组检查的存在是因为
曾经出过一次线上 bug——托管拿"上架槽里那个活的物品对象"作为比对基准，于是清空上架槽的同时也
清空了比对基准，背包因此一个都匹配不上，"上架超过一组"永远报"不够"，无论玩家实际带了多少。
此前所有用例的上架量都不超过槽内数量，从未越过这条边界。

### 手动测试清单

在一个测试世界里执行。两个玩家（或一个玩家加一个 OP）就够了。

1. **余额** —— `/money` → 显示"你的余额为 0.00 Gold"（或你配置的初始余额）。
2. **加钱** —— `/money give <你自己> 100` → 余额变为 `100.00 Gold`。
3. **转账** —— `/pay <对方> 25` → 你的余额减少 25，对方增加 25，且对方会收到提示。
   再验证失败情形：`/pay <对方> 0`（被拒绝）、`/pay <你自己> 5`（被拒绝）、
   `/pay <对方> 999999`（余额不足，且**你的余额必须保持不变**）。
4. **打开市场** —— `/shop`；另外单独放置一个终端并右键它。再确认 `/globalshop open` 也有效。
5. **A 上架，B 能看到** —— 用 A 把 64 个圆石放进上架槽，*上架* 标签页，单价 `1`、库存 `64`、
   起购 `1`、限购 `64`，按 *上架*。确认这 64 个圆石已从 A 的背包中消失。
   用 B 打开市场，确认能看到 A 的商品，显示 A 的名字、单价和库存 64。
6. **B 购买** —— B 选中该商品，数量设为 10。确认面板显示 `1.00 x 10 = 10.00`。按 *购买*。
   确认：B 的余额**精确**减少 10；A 的余额**精确**增加 10；B 拿到 10 个圆石；
   该商品库存变为 54。
7. **余额不足** —— 用 B 把余额花到低于单价（或 `/money set B 0`），再尝试购买。
   确认被拒绝、**B 的余额不变**、且**库存仍是 54**。
8. **购买数量限制** —— 设置起购 2、限购 4：买 1 被拒绝（"低于最少购买数量"），
   买 5 被拒绝（"高于最多购买数量"），买 2~4 成功。
9. **卖家修改** —— 用 A 在 *我的商品* 里把单价改成 `2.50`。用 B 刷新后确认新价格生效。
   提高库存，确认多出来的物品从 A 的背包被扣走；降低库存，确认物品被退回。
10. **下架** —— 用 A 下架。确认剩余物品回到 A 的背包，且该商品从 B 的市场视图中消失。
11. **服务器重启** —— 停掉服务器再启动。确认 `/money` 显示的余额一致，
    未售出的商品依然在，价格和库存也一致。
12. **磁盘文件** —— 确认 `world/data/globalshop_economy.dat` 和
    `world/data/globalshop_shop.dat` 都存在。`config/` 里**不应**出现任何经济数据。
13. **仅服务端生效** —— 用一个没装该模组的客户端连接，确认市场无法打开。

## 9. 替换经济系统

内置经济只是某个接口的一种实现，并且被刻意隔离在独立的包里。

```
com.example.globalshop.economy
├── EconomyService.java        契约：getBalance / addBalance / removeBalance /
│                              transfer / hasEnough / setBalance / ensureAccount
├── EconomyServices.java       接缝：在这里装入你自己的实现
├── InternalEconomyService.java 内置实现
├── EconomySavedData.java      它的服务端存储
├── MoneyFormat.java           long 最小单位 <-> 文本，精确十进制解析
└── TransactionResult.java     一次操作为什么被拒绝
```

要换成你自己的，实现 `EconomyService`，然后在模组初始化时装进去：

```java
EconomyServices.install(server -> new MyEconomyService(server));
```

其他一切都不用改——商店、GUI 和所有指令都通过 `EconomyServices.get(...)` 获取经济系统。

替换实现必须保持两点，因为模组其余部分依赖它们：金额**严格为正**
（方向由你调用哪个方法表达），以及 `transfer` 必须是**原子的**——两边的余额要么都变，要么都不变。

## 10. 如何防止复制物品与刷钱

* **托管，而不是承诺。** 上架会立刻把物品扣走。市场只能发出它真正持有的东西。
* **先校验，后修改。** 所有检查都发生在第一次改动之前，因此一次拒绝不会留下任何
  半完成状态供人重试利用。
* **每次操作一把锁。** 检查与修改在 `synchronized (data)` 内完成，因此两个并发请求
  不可能同时看到"库存还剩 1"或"余额充足"。
* **先收钱，后给货。** 购买先扣买家，转账成功之后才交付物品，因此物品绝不可能在未付款时被交出去。
* **精确算术。** 金额在任何地方都是 `long` 计数的最小单位，并使用
  `Math.addExact` / `Math.multiplyExact`，让溢出被拒绝而不是回绕。
* **不信任输入。** 一个请求最多只携带"哪个商品"和"买几个"。客户端从不需要给出价格、卖家、
  余额或物品，而且交易类网络包只在发送者**确实打开了市场界面**时才会被接受。

### 修改窗口布局时

同时改 `menu/ShopLayout.java`（坐标）和 `tools/make_gui_preview.py` 里对应的那张表，
然后运行该脚本并查看 `tools/gui_preview.png`。它会把三个标签页按 2 倍画出来，
**并打印一份重叠审计报告**。这不是可有可无的礼节：这套预览已经找出过五处元素重叠缺陷
以及一处文字溢出面板的缺陷，而编译器看不见它们。有三条规则保证它可信：

* 预览图里画的每一个字符串都必须是模组**真实渲染**的那个（早先的版本画了一个缩写的余额字符串，
  因此漏掉了真实字符串撞上排序按钮的问题）；
* 面板与网格的**边界也作为矩形纳入比对**，所以文字溢出边缘会被报出来，而不只是元素之间互相碰撞；
* 每个标签页画的是它的**最坏情况**而不是轻松情况——市场页画的是"查看者自己的、附魔过的、有磨损的"
  工具，因为当初画一个普通物品，正是耐久数值与"你的商品"徽标叠在一起却没被发现的原因。

## 本版新增

### 交易佣金
每笔交易按 `marketCommissionPercent`（默认 5%）从交易总额中抽取佣金。买家付全价，卖家收到
总额减去佣金，而**佣金完全离开服务器** —— 不进入任何账户，所以商店是货币回收口，而不是第三个
账户。给卖家的通知里始终写的是**税后**金额，因为那才是他真正收到的数。

### 上架过期
商品在 `listingLifetimeHours`（默认 12）**真实小时**后停止出售。用的是系统时钟而非游戏刻，
所以**服务器关机期间也会过期** —— 这才是要紧的情况。过期商品会从公开市场消失、无法被购买，
但仍留在卖家自己的列表里（图标变暗），且只能下架。把时长设为 0 即可关闭过期。

### 售出通知：离线也不会漏
商品卖出时卖家会收到通知，写明卖了什么、实际收到多少钱。如果卖家不在线，通知会写进世界存档，
在他下次登录时补发 —— 和旁边的物品邮箱是同一套机制。

### VIP
`/globalshop vip` 用游戏内货币购买永久 VIP（价格 `vipPrice`，默认 10000.00）。VIP 最多同时
上架 `vipListingLimit`（20）件，普通玩家为 `listingLimit`（10）。OP 可用
`/globalshop vip grant|revoke <玩家>` 直接授予或收回。市场界面会同时显示**你自己**的身份
（余额左侧）和**所选商品卖家**的身份（卖家名右侧），普通为灰色、VIP 为紫色。

### 补货与一键下架
「我的商品」新增 **补货** 按钮：把你背包里所有该物品一次性加进这个商品 —— 数量由服务端统计，
不会算错；以及 **一键下架** 按钮：一次请求下架你的全部商品，退还托管物品走的是和单个下架
完全相同的那条路径。

### 音效
交易成功播放经验球音效，被拒绝播放村民拒绝音效。判定依据来自**服务端返回的结果**，所以
"看着能点但被拒绝"的情况也会响失败音。

## 崩溃与重启

一笔交易要么整体生效、要么完全不生效：不存在需要修复的半完成状态，因为属于同一笔交易的所有
余额变动和库存变动都在同一个同步块内完成。

崩溃**可能**造成的损失是最后一两笔交易。已完成的交易在内存中，随世界保存落盘，所以在交易后的
几秒内强杀进程会**整笔丢失**该交易，而不会留下半笔。这是有意为之：如果每笔交易都强制写盘，
只要有十几个人同时在买卖，商店就会变成瓶颈。

恢复的思路是：**服务端是唯一权威**。玩家做了什么不存在客户端，客户端的显示缓存在断线时被丢弃，
重新打开市场时第一件事就是向服务端索要当前页面。所以崩溃后玩家看到的正是最后一次保存的状态，
不会有一份过期的本地副本和它打架。

## 本版新增

### 金钱排名
玩家市场窗口（背包左侧）新增 **排名** 按钮，打开全服账户排行榜，按余额从高到低。服务端**最多每
5 分钟重建一次** —— 需求是"每 5 分钟更新一次"，而用缓存刷新而不是主动推送，意味着 100 个人打开
窗口只会重建 1 次而不是 100 次，也不会给任何人发送他没要的东西。窗口顶部会显示这份数据有多旧，
因为一张不说明自己多旧的排行榜，比一张承认自己旧的更糟。

同额时按玩家名排序，所以两个余额相同的人不会在两次刷新之间互换位置 —— 排行榜上同额玩家来回换位，
会让人觉得数字是编的，哪怕每个数字都是对的。榜单包含**所有创建过账户的玩家**（包括已不玩的）。

### 我的交易记录
**交易记录** 按钮打开你自己的玩家间交易历史，最新在前。只保留你**作为买家或卖家**的已完成购买：
上架和下架不算交易，服务器商店另有自己的日志。

请求包里**没有任何"看谁的记录"的参数** —— 所以改过的客户端也**问不出**别人的记录：不是服务端
拒绝，而是这个问题根本无法提出。

每行已按读者视角写好（"卖出 3 个圆石 给 Steve"），金额列标注为**交易额（税前）**：日志记录的是
买家付了多少，佣金是之后扣的，把它叫作"收入"会让卖家看到的钱偏多。

### 物品黑名单（OP）
OP 会多出一个 **黑名单** 按钮，把市场窗口切换成黑名单编辑器 —— **同一个窗口、同一个外框、同一个
背包**，不需要重新学。被禁物品显示在市场用的同一个网格里；把物品放进其他标签页都在用的那个槽位，
点 **禁止上架**；或选中已禁物品点 **解除禁止**。

拦截依据是物品的**注册名**而不是具体那一叠。OP 想表达的规则是"谁都不许卖钻石"；如果按物品叠拦截，
**改个名字就成了绕过规则的办法**。改名或附魔的副本同样被拦，而被拒绝的上架**不会拿走物品**。

检查在 `ShopService.create` 里执行，不是只在界面里。隐藏按钮只是便利，跳过界面的客户端照样被拒。
黑名单**只会发给主动要求编辑器的 OP**，其他人请求会被降级拒绝。

一个已知限制：编辑器网格只有一页 36 项。超出时面板会写明还有多少项未显示，而移除一个可见项就会
露出下一个。

### `/globalshop reload` 现在会真正重读配置文件
Forge **只在启动时读一次配置，并且不监听文件变化** —— 所以在运行中的服务器上改
`config/globalshop-common.toml` 以前是**没有作用**的，原版 `/reload` 也救不了（它重载的是数据包而
不是配置）。现在 `/globalshop reload` 会先从磁盘把文件读进生效的 spec，再应用；找不到文件时会明确
提示。**改配置不需要重启服务器了。**

配置里**不存在任何玩家资产**：只有策略参数，所以改配置永远无法凭空造出钱、物品或商品。

## 一个值得单独说明的修复：那条结果提示此前从未显示过

市场窗口的结果提示 ——「操作成功」「余额不足」，以及现在的「该物品已被服主禁止上架」—— 原本画在
**窗口上方**，理由是那样不会和布局打架。但在 **GUI 区域高度恰好等于窗口高度**的客户端上是看不见的：
窗口高 240，854x480 缩放后的区域也正好是 240，于是窗口顶边在 y=0，而提示被画在 y=-12 —— **屏幕外**。

也就是说，**所有**结果提示其实一直都没被看到过。现在它画在**窗口内部**、内容区顶部，带深色底衬所以
压在什么上面都读得清，并且**按结果显示颜色**：成功绿色、被拒红色。一个和被成功长得一模一样的拒绝，
是读不出"被拒绝"的。

自测现在会遍历 `ShopResult` 与 `ServerShopResult` 的**每一个值**，断言中英文两种语言都有对应文案，
这样以后新增的结果不会悄悄给玩家看一个 `globalshop.result.forbidden_item` 这样的原始键名。

## 邮箱

### 它解决的问题
购买发货用的是 `giveOrDrop`。当买家背包满时，物品会被**丢在地上**，然后被漏斗吸走或被五分钟的消失
计时器清掉 —— 对玩家来说，这和"商店吞了我的钱"没有任何区别。两个商店都有这个问题：玩家市场在购买
时，服务器商店在交付任何物品时。

### 现在的行为
物品先尝试放进背包，**放不下的部分变成邮件**，并在聊天栏告诉玩家。商店**再也不会**把物品丢在地上。

两个商店都投递到**同一个邮箱**，入口是玩家市场窗口里的 **邮箱** 按钮。做成一个而不是每店一个：
同一件事要去两个地方找，对"我买的东西去哪了"来说是更差的答案；而每封邮件都标注了它来自哪个商店。

| | |
|---|---|
| 上限 | `mailboxLimit`，默认 **100** 封 |
| 有效期 | `mailLifetimeDays`，默认 **14** 真实天 |
| 领取 | **左键**点邮件 |
| 删除 | **右键**点邮件 |

一封"邮件"是一次投递，不管它需要几个格子 —— 128 个圆石是 1 封而不是 2 封，因为玩家的感受是这样。

### 几条要紧的规则

**在扣钱之前就会拒绝**：如果物品既放不进背包、也放不进邮箱，购买会被**提前拒绝**并提示玩家清理空间。
卖了东西再把东西销毁不是一个选项；而事后再拒绝意味着要回滚一笔已经完成的付款。

**过期邮件不能领取，只能删除。** 它会以灰色继续显示，让玩家看得到自己损失了什么、为什么，而不是
悄悄消失。过期邮件**也不占**上限 —— 一箱旧邮件会在新邮件到来时自动腾出位置，玩家不会因为邮箱塞满
旧邮件而永远收不到东西。

**部分领取不会重置计时。** 如果只有一部分放得进背包，剩下的会以**原始创建时间**继续留在邮箱里。
如果重新计时，玩家就能靠每次只领一点让一封邮件永远不过期 —— 而这恰恰是有效期要防的事。

**领取时先把邮件取出，再放置物品。** 中途崩溃的话，邮件还在世界存档里（下一次保存才会写入，而那次
保存会同时带上两边的改动），不会出现"邮件还在、背包里也有一份"的情况 —— 那是凭空造物品。

### 升级说明
邮箱以前存的是一串没有任何时间的物品叠（退还的库存、离线结算）。升级时它们会被读成"此刻创建的邮件"：
给一个全新的有效期是**更宽容**的读法，而在升级时丢掉玩家的物品不是。

## 私聊交易窗口

### 入口在哪
玩家市场窗口**右下角的空位** —— 就在「上架槽位」那一格的下方，那块地方之前没人用。

### 玩家列表
经济系统见过的**所有玩家**，一页 5 个，带搜索框。**在线玩家排在前面**，然后按名字排序：
"现在能说话的人"不该需要你在一百个离线名字里翻。

名字在服务器说该玩家已连接时显示为**红色 +（在线）**，否则**灰色 +（离线）**。这个标记是
**服务端在生成页面时决定的** —— 它是事实，而不是客户端拿一份过期的玩家列表猜出来的。

### 聊天
点一个玩家就进入对话。窗口显示你们俩说过的话（最新在前，自己的行一种颜色、对方另一种），
带消息输入框，标题行仍然显示对方名字和在线状态。

**发给离线玩家的消息会被接收，而不是拒绝。** 消息保留下来，并在对方下次登录时通知他：

> 你有 2 则新的私聊留言。
> 查看位置：玩家市场 → 右下角的「私聊交易」按钮。

第二行才是关键：**玩家找不到的消息，等于没送达**，所以通知必须说明去哪看。通知**每则只发一次**：
登录五次不等于被提醒五次。

### 支付
一个金额输入框 + **支付**按钮，直接付给正在对话的玩家。用的是和 `/pay` 指令**完全相同**的
原子转账，所以从窗口付和从指令付不可能有不同结果。对方**可以离线** —— 余额按 UUID 记账，
钱无论如何都是他的。

金额是以**文本**传输的，不是客户端算好的数字。`MoneyFormat` 由配置文件决定，而**客户端的配置
不一定和服务端一致** —— 所以由服务端用他自己的设置解析玩家真正输入的内容。

### 你的背包，是真的槽位
窗口把玩家自己的背包和快捷栏做成**真正的容器槽位**，位置和市场窗口**完全一样** ——
已经记住自己东西在哪的人，不该再找一遍。Shift+点击在背包和快捷栏之间移动。

### 它有意不做什么
**没有物品托管。** 这个窗口提供的是"商量的地方"和"付钱的方式"；物品本身还是像以前一样，
两个人见面交换。在这里另做一套托管，等于在市场之外再造一个交易系统，还要定义"谁能拿回什么"，
而需求里并没有要求这个。如果你要**正式的双向交易窗口（带双方确认）**，那是一个独立的、更大的功能。
